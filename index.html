Case Study 01 · In Progress
VibeCheck — Music Recommender App
Qualcomm Industry-Sponsored Capstone · Machine Learning Intern · Jan 2026 – Present
↗ View on GitHub
What it is
An Android app that recommends songs by fusing three live input signals — a text query, an optional camera frame, and real device sensor readings (accelerometer, light, GPS, clock) — through a 6-stage on-device ML pipeline. All inference runs locally using TensorFlow Lite with NNAPI delegation for NPU acceleration on Qualcomm Snapdragon SoCs. No server required.
The pipeline
Text is encoded by MobileBERT into a 128-d embedding. Images go through EfficientNet-B0 (int8 quantized). Sensor readings are projected to 32-d via a small MLP. The three modalities are aligned to 128-d and fused via weighted average (vision 60%, text 25%, sensors 15%), then projected into song embedding space and ranked by cosine similarity against pre-computed Spotify track embeddings.
The key engineering decisions
Running MobileBERT, EfficientNet-B0, and a sensor MLP concurrently on a phone required careful threading — the three encoders run in parallel coroutines, with fusion happening only after all three complete. Getting NNAPI delegation right for Qualcomm's Hexagon NPU added another layer: model quantization had to be tight enough to benefit from NPU acceleration without degrading embedding quality. We also built graceful fallback heuristic encoders for when TFLite assets aren't available (e.g. on emulators), so the full pipeline stays testable without physical hardware. The eval suite covers latency, accuracy, memory, and pipeline correctness across 12 test classes.

Case Study 03
NYC Taxi Analysis
End-to-end data engineering & ML pipeline · Solo project · Databricks
↗ View on GitHub
What it is
An end-to-end data engineering pipeline built solo on Databricks, processing NYC Yellow Taxi trip data. The pipeline ingests raw parquet files, cleans and transforms them with PySpark, stores the result in Delta Lake, runs SQL analytics, and trains a linear regression model to predict taxi fares.
Why it's interesting
The goal was to go beyond a notebook exercise and build something that mirrors a real production workflow — versioned storage with Delta Lake, reproducible ETL, and a model that actually runs on Spark rather than pulling data into memory. The full NYC dataset is tens of millions of rows, which forces you to think differently about every transformation.
Key technical decisions
Using Delta Lake over raw parquet was a deliberate choice — it gives you ACID transactions and time travel on the processed data, which matters when you're iterating on cleaning logic and don't want to re-run the full ingestion every time. The MLlib linear regression model predicts fare amount from trip distance, duration, passenger count, and pickup location — straightforward features, but the interesting part is that the whole model training runs distributed across the cluster rather than on a single machine.
