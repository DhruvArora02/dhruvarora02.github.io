Case Study 01
VibeCheck — Music Recommender App
Qualcomm Industry-Sponsored Capstone · ML Engineering · Jan 2026 – Present
↗ GitHub
What it is
An Android app that recommends songs by fusing three live input signals, a text query, an optional camera frame, and real device sensor readings (accelerometer, light, GPS, clock), through a 6-stage on-device ML pipeline. All inference runs locally using TensorFlow Lite with NNAPI delegation for NPU acceleration on Qualcomm Snapdragon. No server required.
The pipeline
Text is encoded by MobileBERT into a 128-d embedding. Images go through EfficientNet-B0 (int8 quantized). Sensor readings are projected to 32-d via a small MLP. The three modalities are fused via weighted average (vision 60%, text 25%, sensors 15%), then ranked by cosine similarity against pre-computed Spotify track embeddings.
Key engineering decision
Running MobileBERT, EfficientNet-B0, and a sensor MLP concurrently required careful threading. The three encoders run in parallel coroutines, fusing only after all three complete. Getting NNAPI delegation right for Qualcomm's Hexagon NPU required tight model quantization without degrading embedding quality. We also built graceful fallback heuristic encoders for emulator testing, so the full pipeline stays testable without physical hardware.

Case Study 02
ShrinkDB
A deduplicating, replicated key-value store in C++17 · Solo project
↗ GitHub
What it is
A C++17 storage engine that deduplicates data into content-defined chunks using a rolling hash, with a write-ahead log, concurrent garbage collection, and live TCP replication.
The pipeline
I built every layer myself, the chunker, the chunk store, the write-ahead log, and the replication protocol, so a crash mid-write cannot corrupt anything.
Key technical decision
Choosing content-defined chunking over fixed-size chunking is why a 6.1x dedup ratio holds up even under edits, and getting the reclaim locking right against live reads took several rounds of multithreaded testing.

MCP server for agentic telephony actions · Solo project · Twilio + Anthropic API
↗ GitHub
What it is
An MCP server that lets an AI agent send texts, place calls, and confirm delivery through Twilio and the Anthropic API.
Why this is unique
Unlike most MCP demos, it wraps a real, irreversible action instead of a read-only lookup, so a mistake reaches an actual phone.

Case Study 04
Job Lead Radar
Personal job search automation agent · Solo project · Internal tool
↗ GitHub
What it is
Job Lead Radar is an agent I built for my own job search. It polls company career-page APIs, Greenhouse and Lever, for new postings, filters them against configurable title rules, scores each one for relevance against my resume using Claude, and writes a ranked daily digest. Instead of manually checking a dozen career pages every day, I run one command each morning and get a sorted shortlist already deduplicated against postings I have seen. Right now it is an internal tool, no UI, just a CLI and a markdown digest.
Why this is unique
Most job-tracking tools are keyword scrapers or thin wrappers around LinkedIn scraping, which risks account bans. Job Lead Radar stays inside official public APIs and uses an LLM to actually read each posting and judge fit and seniority, catching cases a title alone would miss. It is also intentionally not an auto-apply bot, every outreach decision stays human in the loop, which keeps it honest as a tool rather than spam.
Hardest part
The trickiest part was not the scoring, it was getting the filtering logic correct before trusting it to discard data permanently. A naive substring exclude list, using "iv" to catch "Engineer IV," silently matched unrelated words like "Delivery" and "Hawaii." Fixing this meant switching to whole-word matching with regression tests for those exact collisions, plus a dry-run mode that shows what would be deleted and why before anything actually gets removed. That verify-before-delete discipline mattered, since the cost of a silent false positive is a good lead you never know you missed.

Case Study 06
NOMinate — Smart Meal Planner
Full-stack personal project · React + Flask + OpenAI
↗ GitHub
What it is
A personalized meal recommendation app that suggests dishes based on cuisine taste, dietary restrictions, budget, cooking skill, and real-time user feedback. Users can choose to cook a recipe or order takeout, and the app adapts by filtering out recent or disliked meals.
My role
Built the full stack end-to-end, React frontend, Flask backend, and OpenAI GPT-3.5 for generating recommendations, ingredient lists, and restaurant suggestions based on user preferences and feedback history.
Key challenge
The interesting engineering problem was prompt design. Structuring the OpenAI calls so recommendations stay personalized and non-repetitive across sessions while respecting dietary restrictions was key. A naive prompt gives you the same 5 meals every time. The solution was injecting recent history and explicit dislike signals into each prompt so the model has enough context to avoid repetition without needing a database of embeddings.
