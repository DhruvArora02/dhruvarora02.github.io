Case Study 01 · In Progress
VibeCheck — Music Recommender App
Qualcomm Industry-Sponsored Capstone · Machine Learning Intern · Jan 2026 – Present
↗ GitHub
What it is
An Android app that recommends songs by fusing three live input signals — a text query, an optional camera frame, and real device sensor readings (accelerometer, light, GPS, clock) — through a 6-stage on-device ML pipeline. All inference runs locally using TensorFlow Lite with NNAPI delegation for NPU acceleration on Qualcomm Snapdragon. No server required.
The pipeline
Text is encoded by MobileBERT into a 128-d embedding. Images go through EfficientNet-B0 (int8 quantized). Sensor readings are projected to 32-d via a small MLP. The three modalities are fused via weighted average (vision 60%, text 25%, sensors 15%), then ranked by cosine similarity against pre-computed Spotify track embeddings.
Key engineering decision
Running MobileBERT, EfficientNet-B0, and a sensor MLP concurrently required careful threading — the three encoders run in parallel coroutines, fusing only after all three complete. Getting NNAPI delegation right for Qualcomm's Hexagon NPU required tight model quantization without degrading embedding quality. We also built graceful fallback heuristic encoders for emulator testing, so the full pipeline stays testable without physical hardware.

Case Study 03
NOMinate — Smart Meal Planner
Full-stack personal project · React + Flask + OpenAI
↗ GitHub
What it is
A personalized meal recommendation app that suggests dishes based on cuisine taste, dietary restrictions, budget, cooking skill, and real-time user feedback. Users can choose to cook a recipe or order takeout, and the app adapts by filtering out recent or disliked meals.
My role
Built the full stack end-to-end — React frontend, Flask backend, and OpenAI GPT-3.5 for generating recommendations, ingredient lists, and restaurant suggestions based on user preferences and feedback history.
Key challenge
The interesting engineering problem was prompt design — structuring the OpenAI calls so recommendations stay personalized and non-repetitive across sessions while respecting dietary restrictions. A naive prompt gives you the same 5 meals every time. The solution was injecting recent history and explicit dislike signals into each prompt so the model has enough context to avoid repetition without needing a database of embeddings.

Case Study 04
NYC Taxi Analysis
End-to-end data engineering & ML pipeline · Solo project · Databricks
↗ GitHub
What it is
An end-to-end data engineering pipeline built solo on Databricks, processing NYC Yellow Taxi trip data across tens of millions of rows. Ingests raw parquet files, cleans and transforms with PySpark, stores in Delta Lake, runs SQL analytics, and trains a linear regression model to predict taxi fares.
Why it's interesting
The goal was to go beyond a notebook exercise and mirror a real production workflow — versioned storage with Delta Lake, reproducible ETL, and a model that trains distributed across the cluster rather than pulling data into memory. At tens of millions of rows, every transformation decision has cost.
Key technical decision
Using Delta Lake over raw parquet was deliberate — it gives ACID transactions and time travel on processed data, which matters when iterating on cleaning logic without re-running full ingestion every time. The MLlib linear regression model predicts fare amount from trip distance, duration, passenger count, and pickup location — the interesting part is that training runs distributed across the cluster rather than on a single machine.
